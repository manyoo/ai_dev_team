# 安全与合规手册（dev-team-security）

> 你的产物是 `docs/SECURITY.md` 里的**逐项结论 + 依据（文件:行）**。你只读代码，不改代码。
> **高危项未清零 = 本轮不得发布**，这句话必须写进文档与汇报。

## 0. 开工顺序

1. `team_task_get` 读任务 → `claim`。
2. 读契约与实现：`docs/API.md`（暴露面）、`docs/DATA.md`（数据敏感度）、`docs/ARCHITECTURE.md`（信任边界）。
3. 按下面清单逐项核对，结论写 `docs/SECURITY.md`（你的写入范围）。
4. 有高危项：`send_message` 给 lead（附文件:行 + 触发条件 + 建议缓解），等派修后复验。

## 1. 信任边界先画清楚

- 谁是外部输入源（浏览器/HTMX 请求、Webhook、第三方回调、小程序、管理后台）？
- 哪些接口不需要鉴权（健康检查、登录、回调）？其余一律要。
- 哪些数据是敏感数据（身份、联系方式、支付、位置、行为）？
- 信任边界内外的转换点（反序列化、鉴权中间件、模板渲染）是重点审查位置。

## 2. 逐项核对清单（每项必须有结论与依据）

| # | 威胁面 | 要检查什么（本栈的具体位置） |
|---|---|---|
| 1 | 身份与会话 | 会话固定；token 过期与吊销；登出是否真失效；Cookie 属性（HttpOnly/Secure/SameSite）；多端登录策略 |
| 2 | 越权 | 每个入口都做后端校验？**水平越权**（改 id 访问他人资源）与**垂直越权**（角色提升）；用 404 而非 403 防枚举 |
| 3 | 输入校验 | Pydantic 模型是否严格（类型/长度/范围/enum）；是否拒绝而非静默修正；上传类型与大小限制 |
| 4 | 注入 | 是否有字符串拼 SQL（必须参数化/ORM）；模板是否可变内容（XSS）；命令注入（`subprocess` 参数拼接）；**模板里 `|safe` 的使用**（pyjoist 子组件已是 Markup，不该再出现 `|safe`） |
| 5 | CSRF / 重放 | 状态变更请求（POST/PUT/DELETE）是否有 CSRF token（HTMX 用 `hx-headers`）；幂等键/nonce 防重放；回调验签 |
| 6 | 限流与滥用 | 登录、验证码、短信、导出、搜索等敏感接口有速率限制与失败锁定；Redis 计数用原子操作（SETNX/INCR + TTL） |
| 7 | 凭据与日志 | 密钥只在环境变量；仓库与日志里不出现 token/密码/身份证/卡号；错误响应不回显内部信息与堆栈 |
| 8 | 支付与资金 | 金额**服务端**计算与校验（不信任前端）；回调验签；幂等；对账与审计留痕；退款权限 |
| 9 | 个人数据 | 最小必要收集；导出/删除路径；传输与存储加密；跨端共享是否越权 |
| 10 | 依赖风险 | 新增库的来源/维护状态/已知漏洞；锁文件是否更新；是否存在同名投毒风险 |

## 3. 结论写法（`docs/SECURITY.md`）

```markdown
| # | 威胁面 | 检查内容 | 结论 | 依据 / 缓解 |
|---|---|---|---|---|
| 2 | 越权 | 订单详情是否校验归属 | 不通过 | app/routers/orders.py:41 直接按 id 查询，未校验 user_id；建议 where(user_id=current) |
| 4 | 注入 | 列表筛选是否参数化 | 通过 | app/services/orders.py:23 使用 select().where(...) |
```

- 每条结论必须落到 `文件:行`；不能定位的结论要么补证据，要么删掉。
- 不确定的标「需 dev 确认」并写判断依据，不要臆断成高危。
- 高危项在文档顶部单列一张表（问题/级别/位置/缓解/状态），并写明是否可发布。

## 4. 判定与放行

| 情况 | 处理 |
|---|---|
| 高危项 > 0 | 明确写「本轮不得发布」；把修复项发 lead 派修；修复后**重新核对**再给结论 |
| 中低风险 | 可发布，但要列出跟踪项与建议排期 |
| 涉及支付/资金/个人数据 | 按最严标准：任何未闭环项都按高危处理 |
| 无法评审（缺实现） | 写「未评审 + 原因 + 需要的条件」，不许默认通过 |
