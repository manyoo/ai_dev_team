# 团队运营模型（Operating Model）

> 这份文件回答：**怎么让这支团队稳定地、快速地、可核查地做出高质量软件。**
> 与 [TEAM.md](TEAM.md)（角色与协作总览）、[DOCS.md](DOCS.md)（文档协议）配套；
> 机器可读的那份在 [`cordis.patch.yml`](../cordis.patch.yml)：`riskTiers`、`pipeline`、`roles`、`projectDocs`。
> 改这里就要同步改配置，改配置也要同步改这里。

## 0. 五个目标 → 对应机制

| 目标 | 机制（不是口号） |
|---|---|
| **正确** | 契约先行（接口/数据先写进 `docs/`）＋ 需求非目标与边界矩阵 ＋ 验收标准逐条可判定 ＋ 独立验证 ＋ Lead 亲验 |
| **有效** | 任务按阶段切分并带依赖，谁在等谁一眼可见；测试计划前置；评审只在高风险时介入，不空转 |
| **快速** | 风险分级（小改走快车道）＋ 契约冻结后并行 ＋ 测试计划与实现并行 ＋ WIP 上限防抖动 |
| **稳定** | 迁移 expand/contract ＋ 开关与回滚方案 ＋ 可观测性 ＋ 事故通道（先止血后复盘）＋ 明确的写入范围（无覆盖写） |
| **高质量** | 六道门 ＋ DoR/DoD ＋ 证据制（没有命令与结果不算完成）＋ 度量与每轮改进 |

## 1. 五条第一原则

1. **契约先行**：接口与数据模型进 `docs/API.md` / `docs/DATA.md` 之后才写实现；契约冻结后变更要走变更控制。
2. **证据制**：交付必须带「跑了什么命令、结果是什么」。L0（口头）不算证据。
3. **单一所有者**：每个文件/目录在同一时刻只有一个写入者；共享文件串行化。
4. **小步可逆**：每个任务小到能在一次会话内完成并验证；每一步都能回滚。
5. **尽早并行**：能并行的绝不串行——测试计划、前端、文档、迁移评审都可以在设计定稿后立刻开始。

## 2. 风险分级（开工第一件事）

**Lead 建队前必须先定级**，等级决定角色、阶段与门禁：

| 等级 | 判定 | 典型例子 | 成员 | 门禁 |
|---|---|---|---|---|
| **T0** | 只改 md/注释/文案，不碰代码 | 改文档、加注释、调文案 | 不建队，Lead 自己做 | 无 |
| **T1** | 单模块内的行为修正，**不改**接口与表结构 | 修一个 bug、改校验规则、调样式 | `dev` + `qa` | 测试门、验收门 |
| **T2** | 功能或契约变化：新接口、改响应结构、加字段、跨模块 | 新增列表页 + 分页接口、加一个字段并展示 | `pm` + `dev` + `qa`（可加 `reviewer`/`release`） | 契约门、测试门、验收门（点了 reviewer 就有评审门） |
| **T3** | 高风险：鉴权/支付/资金/个人数据、数据迁移、并发核心路径、架构调整、发布流程 | 登录改造、支付接入、表结构大改、缓存重构 | `pm` + `architect` + `dev` + `qa` + `reviewer` + `security` + `release` | 契约门、测试门、评审门、安全门、发布门、验收门 |

定级拿不准时**取高一级**。等级写进 `dev_team_start(risk="T2")`，也写进 `docs/WORKLOG.md` 的当轮条目。

## 3. 三条流水线 + 事故通道

**快车道（T1）**：`impl → unit → verify → accept`。两人（dev/qa）、四步、无需求文档阶段——小改不值得走全流程。

**标准车道（T2）**：`req → contract → {testplan ∥ schema → impl → unit} → verify → accept`。
关键点：**qa 的测试计划依赖契约（不是依赖实现）**，所以它和 dev 的实现并行；契约一冻结，两条线同时开工。

**高风险车道（T3）**：在标准车道前后各加一段——前面加 `design`（架构与 NFR），后面加 `review → security → release`。

**事故通道（hotfix）**：线上故障时打破流程，优先级最高的只有两件事：
1. **先止血**：回滚或开关关掉功能（要比重写代码快）；只许最小改动，不许顺手重构。
2. **再复盘**：故障小时级内开 `release`/`architect` 复盘，结论写进 `docs/RUNBOOK.md`（现象、时间线、根因、修复、防复发、监控缺口）；等级按 T3 回归，补测试与告警。

## 4. 阶段、产物与完成判定

| # | 阶段 | 所有者 | 输入 | 产物（落盘） | 完成判定 |
|---|---|---|---|---|---|
| 1 | 需求与验收标准 | pm | 用户目标 | `docs/PROJECT.md`（含非目标） | 每条验收标准可判定；非目标 ≥3 |
| 2 | 架构设计与 NFR | architect | 需求 | `docs/ARCHITECTURE.md`、`docs/DECISIONS.md` | 模块边界、依赖方向、性能/安全/可观测性要求写明 |
| 3 | 接口与数据契约 | dev | 需求（+设计） | `docs/API.md`、`docs/DATA.md` | 每接口有请求/响应/错误码；每表有字段/索引；契约冻结 |
| 4 | 测试计划与用例清单 | qa | 契约 | `docs/TESTING.md`（用例矩阵） | 覆盖边界/失败/权限/并发/HTMX 双分支 |
| 5 | 数据模型与迁移 | dev | 契约 | `migrations/`、`docs/DATA.md` | 空库 `upgrade head` 通过；expand/contract 规划清楚 |
| 6 | 实现 | dev | 契约 + 迁移 | `app/`、`templates/` | 代码可运行；分层与 pyjoist 规范达标 |
| 7 | 单元与渲染测试 | dev | 实现 | `tests/unit/` | 新逻辑与组件渲染有断言；本地全绿 |
| 8 | 独立验证与报告 | qa | 实现 + 测试计划 | `tests/integration/`、`docs/TESTING.md` | 命令与结果原样记录；失败项有最小复现 |
| 9 | 代码评审 | reviewer | 验证后的增量 | `docs/REVIEWS.md` | 每条结论定位到 文件:行；有明确放行结论 |
| 10 | 安全评审 | security | 评审后的增量 | `docs/SECURITY.md` | 威胁面与缓解逐项打勾；高危项清零 |
| 11 | 发布准备与 Runbook | release | 全部产出 | `docs/RUNBOOK.md` | 迁移顺序、开关、回滚、冒烟、告警齐备 |
| 12 | 验收与交付 | lead | 全部产出 | `docs/WORKLOG.md` | Lead 在最新代码上亲自跑验收命令 + 关键路径 |
| A1 | 智能体设计与契约 | agent-dev | 需求 | `docs/AGENTIC.md`（拓扑/状态/工具/提示词/护栏） | 有终止条件、最大步数、成本预算与工具契约 |
| A2 | 智能体实现（LangGraph） | agent-dev | A1 | `app/agents/`、`prompts/` | 图可跑；假模型单测通过；冒烟脚本可用 |
| A3 | 智能体评测与回归 | qa | A2 | `app/evals/`、`docs/TESTING.md` | 通过率/成本/延迟不劣于基线；失败样例有分析 |

阶段由 `dev_team_start` 按等级自动建成**看板任务并连成依赖**：前置未完成时任务是 not-ready，谁在等谁看板上一眼可见。
被点名的角色会把自己那一段（例如 `reviewer`）自动带进流水线。

## 5. 六道质量门

| 门 | 触发 | 通过条件 | 不过怎么办 |
|---|---|---|---|
| **契约门** | 有接口/数据变化 | `API.md` + `DATA.md` 完整且冻结 | 退回契约阶段，禁止写实现 |
| **测试门** | 每个任务 | `uv run pytest -q` + `ruff check` 全绿；qa 报告带命令与结果 | 修到绿；不许跳过用例 |
| **评审门** | T2 点了 reviewer / T3 | REVIEWS.md 无阻断项 | dev 修完后**重跑验证**再交给 reviewer 复看 |
| **安全门** | T3 / 涉及鉴权支付个人数据 | SECURITY.md 高危清零 | 未清零不得发布 |
| **发布门** | T3 / 影响线上数据与流程 | RUNBOOK 有迁移顺序、开关、回滚、冒烟、告警 | 没有回滚方案 = 不能上线 |
| **验收门** | 每轮交付 | Lead 亲自复跑 + 关键路径走通 + 对照验收标准逐条 | 不通过不许说「完成」 |

**DoR（任务可开工）**：目标自足、写入范围明确、依赖已就绪、验收标准可判定、涉及契约的先有契约。
**DoD（任务可完成）**：产物落盘、测试全绿、证据齐全、**该角色负责的 md 已更新**、无范围外改动、向 lead 的汇报含命令与结果。

## 6. 所有权与写入范围

**单一所有者矩阵**（同一时刻只有一个写入者）：

| 路径 | 所有者 | 说明 |
|---|---|---|
| `app/`、`templates/`、`migrations/` | dev | 迁移目录串行：一次只有一个迁移在写 |
| `tests/unit/` | dev | 实现者的单元与渲染测试 |
| `tests/integration/` | qa | 独立验证者不共用目录 |
| `docs/PROJECT.md` | pm | |
| `docs/ARCHITECTURE.md` | architect | 结构/模块/依赖方向的改动；目录结构变化本身属于 T3，所以 T1/T2 不应改它 |
| `docs/DECISIONS.md` | architect（追加）／lead（汇总） | 谁做决策谁追加，lead 负责收尾补齐 |
| `docs/API.md`、`docs/DATA.md` | dev | 契约的唯一真源 |
| `docs/TESTING.md` | qa | 用例清单与验证报告 |
| `docs/REVIEWS.md` | reviewer | 追加式 |
| `docs/SECURITY.md` | security | 威胁与缓解清单 |
| `docs/RUNBOOK.md` | release | 部署、回滚、事故复盘 |
| `docs/WORKLOG.md` | lead | 追加式交接 |
| `AGENTS.md` | lead | 常驻约束 |

**共享文件协议**（`pyproject.toml`、`uv.lock`、`migrations/versions/`、CI 配置）：改动前 `send_message` 给 lead 报备，由 lead 指定顺序；**同一时刻只允许一个人改**。

**冲突裁决**：看板出现 write-scope 重叠警告时，由 lead 当场裁决（改范围 / 一方等待 / 拆文件），不许「先写再说」。

## 7. 交接协议

交接的判据是**下一个人能不能只靠仓库接着干**。所以每次交接必须同时给「文件」与「消息」：

**消息模板**（`send_message`）：

```
[交接] 任务 <id>（<阶段名>）→ 状态：完成/部分完成
改动：<文件:行 或 路径列表>
验证：<命令> → <结果摘要>；手工路径：<...>
文档：<更新了哪些 md，哪一节>
给下一个人：<从哪开始、注意什么、未决问题>
风险/阻塞：<无 / 具体>
```

**交接物清单**（不同阶段必须留下的东西）：

| 从 → 到 | 必须留下 |
|---|---|
| pm → dev | 验收标准、非目标、边界矩阵（PROJECT.md） |
| architect → dev | 模块边界、依赖方向、NFR 要求（ARCHITECTURE.md） |
| dev（契约）→ qa | 冻结的 API/DATA 契约 |
| dev（实现）→ qa | 改动清单 + 自测命令与结果 |
| qa → reviewer/lead | 验证报告（命令+结果）、失败项最小复现、未覆盖项 |
| reviewer → lead | 阻断/建议清单 + 放行结论 |
| security → release | 高危项清零确认 |
| release → lead | 部署顺序、开关、回滚、冒烟结果 |
| lead → 用户 | 「做了什么 / 怎么验证 / 遗留与风险」 |

## 8. 证据等级与验证

| 等级 | 形式 | 是否算证据 |
|---|---|---|
| L0 | 「已完成」「应该没问题」「我检查过了」 | ❌ |
| L1 | 有人跑过但没留输出 | ❌ |
| L2 | 命令 + 结果摘要（`uv run pytest -q` → 42 passed） | ✅ 可接收 |
| L3 | 原始输出/日志 + 可复现步骤（含失败项的最小复现） | ✅ 最强，高风险必用 |

规则：
- **写代码的人不批准自己的代码**：qa 独立复跑，Lead 亲自验关键路径。
- **改了就要重验**：评审后或修复后再次改动，必须重跑测试门，不要沿用旧的「通过」。
- **未验证要明说**：不能验证就写「未验证 + 原因 + 需要的条件」，不许含糊通过。
- **不要用旧证据**：证据绑定当前提交/工作区状态，改动后作废。

## 9. 并行、WIP 与节奏

- **WIP 上限 3**：同时 in-progress 的任务不超过 3 个（Lead 也不必更多）；先完成再开始，避免半成品堆积。
- **依赖就绪才开工**：任务前置没完成时不要「先写个大概」，返工比等待贵。
- **契约冻结点是并行的起跑线**：冻结后 dev 实现、qa 写集成用例、前端做页面、文档同步更新可以同时进行。
- **一人多任务串行**：同一成员的任务按依赖顺序做，不并发切换（上下文切换的成本对 agent 同样成立）。
- **等待是有成本的**：Lead 在等待时不要空转——更新 WORKLOG、清理看板、准备验收命令。
- **长任务拆小**：单个任务超过一次会话能验证的规模，就拆成两个任务并连依赖。

## 10. 度量与每轮改进

每轮收尾时 Lead 在 `docs/WORKLOG.md` 记四个数（一行）：

| 指标 | 定义 | 目标方向 |
|---|---|---|
| 一次通过率 | 首次交给 qa 就通过的任务 / 总任务 | ↑ |
| 返工次数 | 因契约/需求/范围问题返工的任务数 | ↓ |
| 门禁失败点 | 哪道门拦住了（契约/测试/评审/安全/发布/验收） | 前移（越早发现越便宜） |
| 阻塞时长 | 成员等 lead 决策/等依赖的累计时间 | ↓ |

连续两轮同一道门反复失败 → 下一轮必须做一次结构性改进（补契约模板、补测试骨架、调整分工或范围），并把结论写进 `docs/DECISIONS.md`。

### 智能体项目的额外面（A1–A3 阶段）

- **评测门**：评测集与阈值进仓库；改提示词/模型/工具必须跑回归，低于基线不进验收（`verify` 用软依赖等 `agenteval`）。
- **成本门**：单次会话 token/成本上限 + 实际统计；超预算降级或拒绝，不许静默烧钱。
- **可控性**：控制流在图（LangGraph）上，不在提示词里；有最大步数、超时、终止条件与重复调用检测。
- **可回滚三件套**：模型版本、提示词版本、代码版本可分别回滚；提示词是发布物（版本号 + hash）。
- **注入与越权**：外部内容（网页/文档/工具结果）当数据不当指令；工具白名单；写操作需确认；trace 脱敏。

## 11. 稳定性清单（T2 涉及数据/T3 必查）

- **迁移 expand/contract**：先加（可空/带默认）→ 双写或回填 → 切读 → 再删旧列；大表回填分批。
- **回滚**：每个改动都要能回答「怎么退回去」；不能回滚的要写明原因与缓解。
- **开关**：新功能默认走开关，出问题一键关闭，不必回滚代码。
- **可观测性**：新接口有请求日志与错误计数；关键路径有延迟指标；错误日志带请求 id。
- **容量与索引**：新查询走没走索引（EXPLAIN）、列表有无分页、缓存有无 TTL、限流是否需要。
- **依赖**：新增库要说明理由、维护活跃度与替代方案（写进 DECISIONS.md）。
- **密钥**：只在环境变量；日志与仓库里不出现。

## 12. 事故通道（Incident）

| 级别 | 判定 | 动作 |
|---|---|---|
| S1 | 全站不可用 / 数据损坏风险 | 立即回滚或关开关；通知用户；Lead 直接指挥；先不做任何重构 |
| S2 | 核心功能不可用 | 同上，优先止血；可先用降级方案 |
| S3 | 局部异常可绕过 | 排期修复，走 T1/T2 |

纪律：**止血优先于找根因**；所有变更与时间点记进 `docs/RUNBOOK.md`；复盘只谈系统与流程（不加压个人）；防复发项必须变成任务（补测试、补告警、补文档）。

## 12.1 容量上限（加角色前先算人数）

- 团队上限由 `maxMembers`（默认 8）决定，实际值必须与 agent-team 组合包一致（插件与本仓库测试都会比对）。
- **超编要提前失败**：名册超过上限时，建队不建任务、不建成员，直接报错并给出三种选择——去掉点名/连带角色、降一级或拆两轮、两边一起提高上限。
- 典型边界：T3 静态 7 人 + 一个客户端角色 = 8（可行）；**T3 + React + 小程序 = 9（超编）**，必须二选一或拆轮。
- 加角色前先问：它的阶段能拦住什么？只加"看起来有用"的角色会同时吃掉预算和注意力。

## 13. 什么时候加角色

| 条件 | 加谁 | 说明 |
|---|---|---|
| T3，或跨模块/新系统的设计 | `architect` | 定边界与 NFR，避免边写边改结构 |
| 鉴权/支付/个人数据/对外接口 | `security` | 威胁建模与高危项清零 |
| 要上线（CI/CD、迁移顺序、回滚、告警） | `release` | 没有回滚方案不允许发布 |
| 需要独立的代码评审（T2 以上关键改动） | `reviewer` | 写代码的人不批准自己的代码 |
| 富客户端交互 / 独立 SPA | `react-dev` | 只在 HTMX 做不好时 |
| 微信小程序端 | `miniprogram-dev` | 复用同一套 API |
| **以 agent 为核心的智能软件系统** | `agent-dev` | 默认形态：LangChain + LangGraph，模型默认 DeepSeek v4.1 Flash；带进 A1–A3 阶段与评测门 |

加角色用 `dev_team_start(..., roles=["reviewer"])`——被点名的角色会自动把它负责的阶段带进流水线。

## 14. 失败模式 → 对策

| 失败模式 | 症状 | 对策（本模型里的位置） |
|---|---|---|
