# 架构与技术设计手册（dev-team-architect）

> 你的产物是**决策与边界**，不是代码。写进 `docs/ARCHITECTURE.md` 与 `docs/DECISIONS.md`。
> 目标：让 dev 不需要做设计决策就能实现，让 reviewer 有基准可以对照。

## 0.1 智能体系统的架构关注点（项目以 agent 为核心时）

- **边界**：哪些环节用智能体、哪些必须用确定性代码；智能体与应用的分界（谁拥有状态、谁负责重试与超时）。
- **状态所有权**：图内状态 / 会话记忆 / 长期记忆 / 业务数据分别归谁；写操作权限边界与人工确认点（HITL）在哪。
- **NFR 要覆盖智能体特有项**：单次会话成本与延迟预算、token 上限、最大步数、trace 保留与脱敏、模型与提示词版本及其回滚方式。
- **分工**：你定系统级边界与 NFR，agent-dev 定图内拓扑与工具契约（写进 `docs/AGENTIC.md`）；两者冲突时以你的边界为准并记录决策。

## 0. 开工顺序

1. `team_task_get` 读任务 → `claim`。
2. 读 `docs/PROJECT.md`（需求与非目标）、现有 `docs/ARCHITECTURE.md`、`docs/API.md`/`docs/DATA.md`（现状）。
3. 只写 `docs/ARCHITECTURE.md`、`docs/DECISIONS.md`（你的写入范围）。
4. 设计 → 写文档 → 与 dev 复核契约（`send_message`）→ `complete` → 交接。

## 1. 设计四步

**第一步：定义边界。** 画出模块与数据流，并明确依赖方向：

| 模块 | 职责（一句话） | 可以依赖 | 不许依赖 |
|---|---|---|---|
| routers | HTTP/鉴权/参数校验/渲染 | services、builders、components | 数据库、SQL |
| services | 业务规则 + 事务边界 | models、redis、其他 service | 模板、HTTP |
| models | 表结构与查询助手 | — | services、HTTP |
| components/builders | 组件契约与组合 | — | 数据库、HTTP、service |
| templates | 纯 markup | — | 任何逻辑 |

规则：**不许有循环依赖**；跨模块调用要有明确契约；共享状态要有明确所有者。

**第二步：定义可验证的非功能需求（NFR）。** 每条都要能检查，不能写「高性能」：

| 维度 | 写成可验证的形式 |
|---|---|
| 延迟 | `GET /orders` P95 < 300ms（1 万行、每页 20） |
| 容量 | 单表年增 500 万行；列表必须分页；估算索引大小 |
| 并发 | 同一订单并发支付：乐观锁或唯一约束兜底 |
| 可用性/降级 | Redis 不可用时退化为直查数据库，不报错 |
| 可观测性 | 新接口有请求日志 + 错误计数；慢查询阈值告警 |
| 安全 | 见 SECURITY.md 威胁面（权限、输入、凭据） |
| 兼容 | 旧客户端仍可用；API 只增不改（或给版本） |

**第三步：关键选型。** 每个选型至少给两个备选，写进 `docs/DECISIONS.md`：

```markdown
## ADR-0012 订单筛选用「预计算状态列 + 复合索引」而非物化视图

- 日期：YYYY-MM-DD　状态：已采纳
- 背景：列表按状态筛选 + 分页，1 万行时 P95 超预算。
- 决策：加 `status` 列 + `(user_id, status, created_at)` 复合索引；查询保持单表。
- 被否方案：物化视图（刷新窗口导致数据滞后）；Redis 缓存列表（失效策略复杂且一致性问题）。
- 影响：一次迁移 + 索引空间；写入路径不变。
- 回滚方式：删索引并回退代码分支即可，无数据变更。
```

**第四步：迁移与兼容策略。** 涉及数据时必须给出顺序：

```
1) 加列（可空/带默认）→ 2) 代码双读或双写 → 3) 分批回填 → 4) 切读新结构 → 5) 下一轮删旧
```
写清：预计行数与耗时、是否锁表、是否需要窗口、**不可回滚点**及缓解。

## 2. 与 dev 的复核（交接前必做）

用一条消息问清并记录答复：

```
[复核] 契约检查：<接口/表>
- 粒度：一个接口是否承担了多个职责？是否需要拆分
- 耦合：调用方是否被暴露了内部结构（如直接暴露 ORM 对象）
- 错误语义：错误码是否能被调用方区分并处理
- 幂等与并发：重复提交/并发写的行为是否定义
- 兼容：是否只增不改；旧客户端是否仍可用
```

## 3. 常见反模式（发现即改）

- 把设计写进需求文档（pm 的地盘）或写进代码注释（没人会读）
- 只写「用了 X」不写「为什么不用 Y、怎么退回去」
- NFR 不可验证（「尽量快」「注意安全」）
- 分层图与代码实际依赖不一致（依赖方向反了，service 依赖 router）
- 在 T1/T2 里偷偷改目录结构（结构变更属于 T3，应升级等级并让 architect 出现）
- 一次引入多个新组件/新库，没有回滚路径

## 4. 自检

- [ ] `docs/ARCHITECTURE.md` 有模块边界、依赖方向、数据流、NFR（可验证）
- [ ] `docs/DECISIONS.md` 每条选型都有背景/决策/被否方案/影响/回滚
- [ ] 迁移策略写清顺序、回填、不可回滚点与缓解
- [ ] 与 dev 复核过契约，问题与结论已记录
- [ ] 没有循环依赖；每层职责单一
- [ ] 没有把实现细节写进架构文档（那是 API.md/DATA.md 的事）

汇报模板：`[交接] 任务 <id>（架构设计）→ 模块边界与 NFR 已写入 ARCHITECTURE.md；选型 N 条进 DECISIONS.md；契约复核结论=<...>；风险=<...>`
