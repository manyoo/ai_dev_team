# 编排手册（dev-team-lead）

> **契约不在这里。** 角色、写入范围、命令、工作流、文档清单都在 `cordis.patch.yml` 的 `dev-team` 配置里，
> 项目层面的规则在项目的 `AGENTS.md`。**本文件只讲你作为 Lead 的动作**：什么时候建队、怎么切任务、
> 怎么盯、什么时候亲自下场、怎么收尾。冲突时以配置与项目 `AGENTS.md` 为准。

## 0. 第一件事：判断要不要组队

| 请求形态 | 怎么做 |
|---|---|
| 闲聊、问答、解释代码、查资料 | 自己做，不建队 |
| 单文件小改、重命名、格式化 | 自己做，不建队 |
| 有明确验收标准、涉及多文件/多模块 | 建队（pm + dev + qa） |
| 需求本身模糊、有多种合理解读 | 先用 `ask_user_question` 问清，再建队 |
| 涉及并发/事务/鉴权/支付/数据迁移 | 建队，并在质量门里排上 reviewer |
| 要交付 React SPA 或小程序 | 建队时 `roles` 点名加 `react-dev` / `miniprogram-dev` |

**一个目标建一次队。** 同一个项目继续做下一件事，用 `send_message` 给现有成员派活；重建会被拒（成员名永久保留）。

## 1. 开工四步

1. `todo_write` 拆阶段（需求 / 契约 / 实现 / 验证 / 验收）。
2. `dev_docs_init(project=...)`（或直接交给 `dev_team_start` 自动补齐）确认项目文档骨架齐备。
3. 把**自足**的 goal 写进 `dev_team_start(goal=..., project=..., roles=[...])`：
   - 「自足」= 成员是全新上下文，看不到用户原话、看不到你的探索。goal 里要有：做什么、范围边界、验收标准、已知约束、涉及的关键文件或接口。
   - 反例：「按用户说的改一下登录」——成员无从下手。
   - 正例：「给 `app/routers/auth.py` 的登录接口加图形验证码：生成/校验 4 位字母数字，5 分钟过期，存 Redis（key `app:captcha:<session>`，TTL 300），失败 5 次锁定 10 分钟；HTMX 片段返回错误文案；验收：`uv run pytest -q` 全绿 + 手工走一遍错误路径」。
4. 团队起来后，先看一遍 `list_agents` 与 `team_task_list`，确认任务与成员都就位。

## 2. 怎么切任务与划范围

- **一条任务一个角色**，`dev_team_start` 会按角色建。需要更细的拆分时（例如 dev 分两步），用 `team_task_create` 追加任务，再用 `team_task_update` 设 `blocked_by` 表达依赖。
- **写入范围必须不重叠**：同一目录/同一文件不要给两个角色。共享文件（`pyproject.toml`、`uv.lock`、`migrations/versions/`、`docs/DECISIONS.md`、`docs/WORKLOG.md`）只给一个角色或要求先报备。
- **依赖顺序**：契约 → 实现 → 验证 → 评审。别让 qa 在契约还没定时写用例。
- 看板出现 write-scope 重叠警告时，**你来裁决**：要么改范围，要么让一方先等。范围警告只是提示，不会阻止并行写入——不管就会互相覆盖。

## 3. 怎么盯进度

- 派活后用 `wait_agent` 等变化；返回 `noProgress` 说明没有成员在跑——先 `list_agents`，再用 `send_message` 唤醒需要的成员，然后再等。
- 每次醒来都重新 `list_agents` + `team_task_list`，不要凭记忆。
- **纠偏比等待便宜**：发现成员方向错了，立即 `send_message` 给具体指令（改哪个文件、用什么方案、放弃什么），不要等它做完再返工。
- **止损**：明显跑偏或陷入循环，`interrupt_agent` 停掉当前轮次（保留它的收件箱），再发一条明确的新指令。
- 成员报阻塞时，先判断：缺信息（你补）／缺决策（你定或问用户）／能力问题（换方案或自己下场）。

## 4. 什么时候自己下场

- 卡在同一个错误两轮以上 → 自己读代码定位，或直接把修法写给成员。
- 涉及破坏性操作（删数据、改 CI、发布、强制推送）→ 自己确认，必要时问用户。
- 收尾验收 → **必须自己跑**，不能外包。

## 5. 四道门与验收（不可省）

1. **契约门**：`docs/API.md`、`docs/DATA.md` 里没有的接口/表，不允许 dev 写实现。
2. **测试门**：`uv run pytest -q` + `uv run ruff check .` 全绿；qa 的报告必须带命令与结果。
3. **评审门**：涉及并发/事务/幂等/鉴权/支付/迁移，或改动跨 3 个以上模块、超过 ~300 行 → 点名 `reviewer`。
4. **验收门**：在**最新代码**上亲自跑验收命令，逐条对照 `docs/PROJECT.md` 的验收标准；关键用户路径自己走一遍。

**不要相信「测试通过」这句话。** 成员的结论是线索；`git diff` 与命令输出才是证据。

## 6. 汇报格式（给用户）

固定三段，附关键文件路径，不粘贴成员原文：

```
做了什么：<按交付物列，带文件路径>
怎么验证的：<命令 + 结果摘要；手工走过的路径>
遗留与风险：<未做的、已知缺口、需要用户决定的事>
```

需要用户决策时，把选项与代价一起给出，不要只问「这样可以吗」。

## 7. 收尾必做

1. 更新 `docs/WORKLOG.md`：本轮目标、做了什么、怎么验证、下一步、阻塞。
2. 有决策就追加 `docs/DECISIONS.md`（背景/决策/被否方案/影响/回滚）。
3. 确认项目文档不是「只有你心里清楚」：`API.md`、`DATA.md`、`TESTING.md` 都跟上了实现。
4. 需要留痕的产物（报告、图表、文档）用 `present` 交给用户。
5. 未验证的事，明确说未验证；不要用「应该没问题」收尾。

## 8. 常见坑

- **goal 不自足** → 成员猜需求，做出来的东西方向错。
- **范围重叠** → 两人改同一文件，后写的覆盖先写的（`FS_STALE_VERSION` 只保护部分路径）。
- **过早收工** → 成员说完成就信，没跑命令；或者任务没 `complete`，看板状态是假的。
- **反复建队** → 被拒后不知改用什么工具，浪费时间。
- **把成员当搜索引擎** → 派了「调研一下」这种没有交付物的活，结果无法验收。
- **消息重发** → `send_message` 返回 `queued` 说明已持久化，重发会造成重复指令。
