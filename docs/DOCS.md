# 项目文档协议

> 每个项目都必须有一份持续更新的 md 记录（共 13 份）。这份文件定义**有哪些文件、谁维护、什么时候更新、怎么写**。
> 机器可读的清单在 [`cordis.patch.yml`](../cordis.patch.yml) 的 `projectDocs`；骨架模板在 [`templates/project/`](../templates/project)。

## 1. 为什么强制

- **上下文会丢**：会话结束、压缩、换人之后，只剩仓库里的文件能交接。
- **结论必须可核查**：写清命令与结果，别人（和未来的你）才能复现，而不是相信一句「已完成」。
- **git 是审计线**：文档跟着代码一起提交，谁在什么时候决定了什么，一眼可查。

## 2. 文件清单与所有者

| 文件 | 所有者 | 用途 | 更新时机 |
|---|---|---|---|
| `AGENTS.md` | lead | 给所有 agent 的常驻约束（技术栈、命令、目录、pyjoist 规范、文档入口） | 技术栈/命令/目录约定变化时 |
| `docs/PROJECT.md` | pm | 目标、范围、**非目标**、用户场景、术语、验收标准 | 需求或范围变化时 |
| `docs/ARCHITECTURE.md` | architect | 模块边界、依赖方向、请求链路、外部依赖、NFR、运行与部署 | 结构或依赖方向变化时（结构变更属 T3） |
| `docs/API.md` | dev | 路由契约（方法/路径/请求/响应/错误码/鉴权）、HTMX 片段约定、前端使用清单 | **先改这里再写实现** |
| `docs/DATA.md` | dev | 表结构与索引、Alembic 迁移历史、Redis key 空间与 TTL | schema / key 变化时，与迁移同步 |
| `docs/DECISIONS.md` | lead | 决策记录（背景/决策/被否方案/影响/回滚）**追加式** | 每次技术与产品决策 |
| `docs/WORKLOG.md` | lead | 每轮进展与交接（做了什么/怎么验证/下一步/阻塞）**追加式** | 每轮工作结束 |
| `docs/TESTING.md` | qa | 测试策略、用例清单、独立验证的命令与结果、已知缺口 | 每次独立验证后 |
| `docs/REVIEWS.md` | reviewer | 评审记录（文件:行 + 级别 + 建议 + 是否已修）**追加式** | 每次评审 |
| `docs/SECURITY.md` | security | 威胁面 10 项核对、逐项结论与依据、高危项清零记录 | 涉及鉴权/支付/个人数据/对外接口时（高危未清零不得发布） |
| `docs/RUNBOOK.md` | release | 发布顺序、迁移 expand/contract、开关、回滚、冒烟、告警、事故复盘 | 上线/迁移/事故后 |
| `docs/AGENTIC.md` | agent-dev | 智能体拓扑与状态、记忆分层、工具契约、提示词与模型配置、护栏与预算、追踪与评测基线 | 改拓扑/状态/工具/提示词/模型时（改完必须跑评测回归） |
| `docs/FRONTEND.md` | react-dev / miniprogram-dev | React SPA / 微信小程序工程结构、构建发布、对接方式 | 客户端工程变化时（无客户端可留空） |

## 3. 怎么生成

```python
# 新项目先建骨架（只创建缺失文件，不覆盖已有内容）
dev_docs_init(project="myapp")

# 建队时给 project，会自动补齐缺失的文档
dev_team_start(goal="...", project="myapp")
```

- 模板来自本仓库 `templates/project/**`，与上表一一对应。
- 工具**从不覆盖**已存在的文件；某份文档缺模板时会写一个带标题/用途/所有者的占位文件，并在返回的 `missingTemplates` 里报告。
- 工具只允许在工作目录或用户主目录内创建这些文件。

## 4. 写作规则

1. **一个事实只写一处**：接口细节只写 `API.md`；数据字段只写 `DATA.md`；别处需要时用链接引用，不要复制粘贴。
2. **追加式文件只追加**：`DECISIONS.md`、`WORKLOG.md`、`REVIEWS.md` 不重写历史；结论变了就写新条目并注明取代了哪一条（`已被 ADR-XXXX 取代`）。
3. **命令与结果原样记录**：`uv run pytest -q` → `42 passed in 3.1s`。没有命令的结论视为无效。
4. **每条记录带日期**：日期用 `YYYY-MM-DD`；条目首行写清「这一轮/这次评审做了什么」。
5. **写下一步，不只写做过什么**：`WORKLOG.md` 的「下一步」必须具体到文件或接口，让下一个人能直接接手。
6. **待办用 checkbox**：`- [ ]` / `- [x]`，方便扫。
7. **决策必须写被否方案**：只写「用了 X」没有价值，写清「为什么不用 Y」才有价值。
8. **不写密码与令牌**：凭据只写「放在哪个环境变量」。
9. **文档与代码同提交**：一个任务完成时，代码与它对应的 md 一起进同一个 commit。

## 5. 触发时机速查

| 你刚做的事 | 必须更新 |
|---|---|
| 定了一个新需求 | `PROJECT.md`（含非目标） |
| 确定了接口或响应结构 | `API.md` |
| 加了表/字段/索引，或写了迁移 | `DATA.md` |
| 选了库、定了并发或缓存策略 | `DECISIONS.md` |
| 跑完一轮验证 | `TESTING.md`（+ 交接到 `WORKLOG.md`） |
| 评审完一段代码 | `REVIEWS.md` |
| 定了模块边界/NFR/关键选型 | `ARCHITECTURE.md` + `DECISIONS.md` |
| 改了鉴权/支付/个人数据/对外接口 | `SECURITY.md` |
| 要上线、要迁移、出了事故 | `RUNBOOK.md` |
| 改了智能体拓扑/工具/提示词/模型 | `AGENTIC.md` +（评测结果进）`TESTING.md` |
| 一轮工作收尾 | `WORKLOG.md` |
| 客户端工程或对接方式变了 | `FRONTEND.md` |
| 技术栈、命令、目录约定变了 | `AGENTS.md` |

## 6. 反模式

- ❌ 只有对话结论，没有文件记录 —— 换会话即归零
- ❌ 文档写「已完成，测试通过」但不给命令 —— 无法核查
- ❌ 把接口细节抄进 `ARCHITECTURE.md` —— 两处维护必然漂移
- ❌ 实现先写、`API.md` 后补 —— 契约门失效，评审没有依据
- ❌ `WORKLOG.md` 只写「继续开发」 —— 下一个人无法接手
- ❌ 覆盖别人的追加段落 —— 历史记录失真
